# F06 Data Structures and Algorithms Basics 数据结构和算法基础

## 目标

把主教程会反复出现的数据布局、容器选择和基础算法直觉先对齐。

## 读完你应该能做什么

- 理解为什么连续存储对 tensor 很重要
- 理解什么时候 `vector`、`unordered_map` 和简单数组就够了
- 理解复杂度的基本概念，但不把它变成理论课
- 理解为什么这套教程会先选简单算法

## 为什么重要

这套教程里有几种重复出现的数据结构选择：tensor 用连续 buffer，名称查找用 hash map，状态记录用 vector，正确性优先的路径先用简单循环。

如果读者对这些选择不熟，后面的章节会显得比实际更复杂。这里要补的不是抽象课本知识，而是工程直觉：什么数据该连续放，什么数据该索引，什么地方先写最简单的实现。

## 后面会用到什么

- tensor storage 和 view 语义
- ModelLoader 的查找表
- attention 和 matmul 循环
- KV cache 和 runtime state 容器
- benchmark 结果存储

## 这一页的核心内容

### 1. 连续存储优先服务数值数据

当你需要密集数值数据、可预测迭代和共享原始 buffer 时，就应该优先考虑连续存储。

这也是为什么教程里的 tensor payload 会围绕连续 buffer 来设计，而不是一堆分散分配。对推理来说，连续布局的价值不只是“好看”，还包括：

- 更容易做顺序访问
- 更容易共享 view
- 更容易把数据搬到 device
- 更容易和底层 kernel 对接

### 2. 查找结构优先服务命名访问

当你需要按名称快速找到 tensor 或符号时，就用 hash map。

模型加载非常适合这种结构，因为它经常要把文件里的名称映射回对象。这里的工程重点不是“hash map 很快”，而是“命名入口必须稳定，才能把文件语义和程序对象对上”。

### 3. 顺序容器优先服务有序状态

当顺序重要时，就用 vector，比如 layer stack、cache 列表或者结果记录。

在推理引擎里，很多东西本来就是顺序性的：

- layer 的执行顺序
- token 的生成顺序
- 请求的推进顺序
- benchmark 的记录顺序

### 4. 基线算法先追求可读

先用最简单、最容易验证的实现。对这套教程来说，一个清楚的 `O(n^3)` CPU reference，比一个聪明但看不懂的优化更有价值。

原因不是反对优化，而是：

- 基线清楚，后面的优化才有比较对象
- 实现简单，bug 更容易定位
- 先把正确性站稳，再讨论性能收益

教程里描述复杂度时，通常不会做正式推导，而是用直觉表达：

- `O(n^2)` 对推理来说通常太大，除非 `n` 很小
- `O(n^3)` 作为 reference 可以接受，但不会用作生产路径
- `hash map` 的查找几乎是常数，适合 loader 的按名访问

重点不是算复杂度，而是判断“这个规模下这个算法能不能接受”。

### 5. 数据布局决定后续成本

同样的算法，布局不同，后续成本会差很多。

这在教程里会反复出现：

- tensor 连续布局决定 view 和共享是否容易
- loader 查找结构决定解析是否容易定位
- runtime 容器结构决定状态是否容易追踪

这也是为什么基础阶段就要建立“布局先于优化”的直觉。

## 查找结构选择

loader 的查找结构要根据需求选，而不是默认都用同一种容器：

| 需求 | 结构 | 原因 |
| --- | --- | --- |
| 名称查找，顺序不重要 | `unordered_map` | 查找快，最适合 loader 的主路径 |
| 名称查找，需要确定性顺序 | `std::map` | 有序，可复现 |
| 名称查找，数量很小 | `vector` + 线性查找 | 简单，没有额外 hash 开销 |

在这套教程里，loader 通常会优先用 `unordered_map`，因为名称查找是主要操作，顺序不影响正确性。

## 选型表

| 需求 | 优先结构 | 原因 |
| --- | --- | --- |
| 连续数值 buffer | `vector` / 连续数组 | 易于顺序访问、共享和传输 |
| 名称到对象映射 | `unordered_map` | 适合加载和查找 |
| 有序状态或日志 | `vector` | 顺序语义明确 |
| 固定大小的小数据 | `array` / 静态字段 | 约束清楚，开销小 |
| 验证阶段的简单遍历 | 直接循环 | 最容易读、最容易测 |

## 组合视角

`00.5` 讲的是对象如何组合，`00.6` 讲的是对象内部如何选择数据结构。两者是同一件事的两层：

- 对象层：不同对象负责不同职责
- 数据层：同一个对象内部用不同数据结构服务不同访问模式

```cpp
class Model {
public:
    std::unordered_map<std::string, Tensor> tensors_;  // 按名查找
    std::vector<std::string> layer_order_;             // 执行顺序
    std::vector<float> shared_buffer_;                 // 连续存储
};
```

这个例子说明：对象设计和数据结构选择不是两件事，而是同一个模型的两层表达。

## 最小示例

```cpp
#include <unordered_map>
#include <vector>
#include <string>

std::unordered_map<std::string, int> make_lookup() {
    return {{"weight", 1}, {"bias", 2}};
}

int sum_vector(const std::vector<int>& values) {
    int sum = 0;
    for (int v : values) {
        sum += v;
    }
    return sum;
}
```

这个例子展示了教程里最常见的两种模式：

- 用 hash map 做名称访问
- 用 vector 加循环处理顺序数据

如果把它翻成教程里的工程语义，就是：

- 名称查找服务 loader
- 顺序遍历服务 layer、cache 和结果记录
- 连续存储服务 tensor payload 和共享 buffer

## 怎么验证

- 解释为什么 tensor 要用连续存储
- 解释为什么模型参数会用查找表
- 解释为什么 CPU reference 一开始会用简单循环
- 解释哪类数据该按顺序存，哪类数据该按名称查
- 解释复杂度应该怎么用直觉方式判断

## 常见问题

- 还没理解访问模式，就先选数据结构
- 明明 vector 就够了，却用了更复杂的数据结构
- 过早优化，结果让代码更难读
- 把算法复杂度和实际运行成本混为一谈
- 忽略布局，只盯着接口
- 把“快”当成唯一目标
- 试图把复杂度当成数学证明来写
- 没有区分“可接受的 reference”和“生产路径”

实践标准很简单：先匹配访问模式，再去优化实现细节。

## 总结

读完这一章后，读者应该能理解为什么这套教程总是优先使用 vector、hash map 和直接的循环，而不是更复杂的数据结构。

如果你能先解释访问模式，再解释选了什么结构，那么这一章就完成了任务。
