# F04 Debugging and Testing Basics 调试与测试基础

## 目标

介绍这套教程里会用到的调试和测试习惯。

## 读完你应该能做什么

- 理解如何把一个失败步骤单独隔离出来
- 理解小测试和增量验证的价值
- 理解 shape 检查、数值检查和性能检查的区别
- 理解基本日志和观察习惯

## 为什么重要

这套教程是按步骤搭建一个小推理引擎的。只有每一步都能独立检查，这种写法才成立。没有调试习惯时，就很难判断一个失败到底来自当前改动，还是来自前面某一层。

这一章讲的是流程，不只是工具。目标是在系统增长时，仍然能保持实现稳定。

在这套教程里，调试不是写完代码之后才开始的环节，而是实现循环的一部分：每一章都先加一点东西，再确认它还符合预期，然后再继续往前走。

## 后面会用到什么

- tensor ops 和 operator 的单元测试
- 端到端正确性验证
- benchmark 测量
- 中间输出的 shape 和数值验证
- CMake 里单独构建测试程序

## 这一页的核心内容

### 1. 一次只改一件事

每次只做一个改动，只检查一个结果，然后再往前走。一次性改太多，后面很难定位问题。

这对教程尤其重要，因为每章都应该能独立站住。如果两个地方同时坏了，你要知道是哪一章引入了问题。

### 2. 尽早检查中间结果

不要等整个模型都搭完才看结果。只要 tensor shape、数值和简单前向输出已经出现，就应该开始检查。

中间验证是让这个项目不变成黑盒的关键。shape 检查、日志和小而固定的测试，通常就足够判断问题出在数学、数据流还是环境。

### 3. 用断言捕捉非法状态

断言是一个便宜但有效的办法，可以在接近问题源头的地方发现错误假设。

对这套项目来说，断言通常比静默 fallback 更合适，因为它能更早失败，也更容易看出是所有权问题还是 shape 问题。

推理场景里，断言最好写在最靠近错误发生的位置：

```cpp
#include <cassert>
#include <cmath>
#include <vector>

bool close_enough(float a, float b, float eps = 1e-5f) {
    return std::abs(a - b) < eps;
}

void check_matmul_shape(std::size_t a_rows, std::size_t a_cols,
                        std::size_t b_rows, std::size_t b_cols) {
    assert(a_cols == b_rows && "MatMul shape mismatch");
}

void check_index(std::size_t idx, const std::vector<float>& data) {
    assert(idx < data.size() && "Index out of bounds");
}
```

这类断言比“函数最后才报错”更有价值，因为它能直接把问题收缩到 shape、边界或者加载结果上。

### 4. 优先使用可复现的小测试

带固定输入的小测试比很多移动因素的大场景更容易调试。

教程里的章节测试遵循这个原则：输入要小，预期要明确，失败面要窄。

这套教程里的测试方式可以按三层理解：

- 简单断言：用于单文件快速验证
- 独立测试程序：每章一个 `test_xxx.cpp`
- 构建集成：用 `add_executable(test_xxx test_xxx.cpp)` 让 CMake 统一管理

这样不需要引入重型测试框架，也能保持每个测试可单独构建和运行。

### 5. 区分测试类型

- shape 检查：确认维度正确
- 数值检查：确认数值足够接近
- 性能检查：确认延迟或吞吐达到预期

这个区分很重要，因为一个章节可能通过 shape 检查，却在数值检查上失败；也可能这两者都通过，但对目标场景来说还是太慢。

## 最小示例

```cpp
#include <cassert>

int add_one(int x) {
    return x + 1;
}

int main() {
    assert(add_one(1) == 2);
    assert(add_one(0) == 1);
    return 0;
}
```

这个例子说明了三件事：

- 预期行为是明确的
- 错误结果会立刻失败
- 测试足够小，一眼就能看懂

如果是浮点数，通常要用近似比较而不是直接相等：

```cpp
bool approx_equal(float a, float b, float eps = 1e-5f) {
    return std::abs(a - b) < eps;
}
```

## 怎么验证

- 假设错了时测试会失败
- 预期对了时测试会通过
- 用一个最小输入就能复现 bug
- 知道失败时先看 shape、再看数值、最后才看性能
- 知道测试失败后，把案例保留下来做回归用例

如果你能用一个很小的例子复现失败，通常就能判断下一步应该修代码、修测试还是修环境。

一个实用的失败诊断路径可以记成这样：

1. 检查测试是否已经用了最小输入
2. 判断失败类型是 shape、数值还是性能
3. 添加临时日志打印中间值
4. 把失败案例保存成新的测试用例，防止回归

## 日志层级

日志在调试里的作用不是“越多越好”，而是按阶段服务不同目标：

1. 开发期：`std::cout` 打印中间值，快速迭代
2. 调试期：结构化日志保留上下文
3. 运行期：只输出关键信息，避免噪音

教程里最实用的习惯是：

- 开发时大胆打印 tensor shape 和关键中间值
- 提交前把临时输出清理掉，或者降级成条件日志
- 测试失败时，日志是复现路径的第一手资料

## 常见问题

- 一次调试太多变量
- 等整个管线都做完了才开始检查
- 把性能测试当成正确性测试
- 明明一个小固定案例就够，却用了很大的随机输入
- 只看最终输出，不看中间状态
- 日志打印了很多，但没有上下文

如果你为了理解一个失败，不断加日志才看懂，那通常说明测试太大或者问题定义太模糊。

## 与构建的关系

测试和构建最好一起看。`00.2` 负责告诉你怎么把程序构建出来，`00.4` 负责告诉你怎么把测试单独构建出来。

在 CMake 里，一个最小的测试程序通常就是：

```cmake
add_executable(test_matmul test_matmul.cpp)
target_link_libraries(test_matmul PRIVATE engine)
```

这比把测试混进主程序里更清楚，也更容易单独运行和回归。

## 总结

这一章是为这套教程的测试驱动工作流打底。读完后，读者应该能把问题拆成小步调试，而不是对着最终失败点猜原因。

实用结果很简单：每一章都应该有一个清楚的方法证明自己还工作正常，而这一页讲的就是让这个方法成立的习惯。
