# Writing Guidelines 教程编写规范

本文档定义这套教程的最终写作标准，用来保证每章都围绕同一个问题展开，并且能被验证、被维护、被扩展。

## 1. 写作目标

这套教程不是把概念解释得最多，而是把工程问题讲清楚，把最小可验证版本做出来，并且让整条主线能顺着读下去。

每一章都应该明确写出：

- 这一章在解决什么问题
- 这一章为什么现在就要解决
- 这一章的验证命令和通过条件
- 这一章如何自然接到下一章
- 这一章结束时，系统新增了什么能力

## 2. 章节结构

章节结构以学习者的行动顺序为准，而不是以维护者的分类顺序为准：

1. `intro.md`：`先跑起来 -> 这章学什么 -> 跟着做 -> 验证结果 -> 接到下一章`
2. 正文：一个页面解决一个问题，按 `问题 -> 最小例子 -> 实现 -> 验证与下一步` 展开
3. `summary.md`：迁移期间只作为旧链接兼容页；章节收口统一放入 `intro.md`

`intro.md` 最多 4 个二级标题。主图、框架对照、源码入口和下一章提示都嵌入这条顺序，不再为 `summary.md` 建立第二套导航。

背景和设计推导仍然保留，但放在正文的连续叙述中；只有在内容确实跨越多个决策时，才增加一个“为什么这样设计”小节。

### 2.1 正文与学习计划独立

`Foundation`、`Chapter00-09` 和 `reference` 是稳定知识资产；`source/guides/` 下的学习计划是这些资产的可变编排。仓库可以同时维护 CPU 入门、源码阅读、性能优化或 GPU 等多套计划。

- 学习计划可以引用章节、代码、练习和验证命令。
- 章节正文不得引用 `Task 1`、`任务 4` 或“第一期计划”等具体计划编号。
- 正文只描述技术依赖，例如“先完成 Chapter03 的 MatMul 契约”，不描述某套计划中的先后编号。
- 通用脚本、记录模板和验收工具按技术产物命名，避免命名为 `task4_*`。
- 调整、增加或删除学习计划时，不要求改写章节正文。

### 2.2 学习者内容与维护内容分离

学习者页面包括根 README、站点首页、阅读指南、Foundation、Chapter00-09、guides、reference 和 exercises。维护内容只保存在 `source/maintenance/`、`SESSION_HANDOFF.md` 和贡献者入口中。

- 学习者页面只写可执行的学习目标、运行条件、技术限制和验收标准。
- 教程建设进度、英文覆盖率、当前就绪度、P0/P1、缺口清单和内容补强顺序不得出现在学习者导航中。
- “当前没有 CUDA backend”这类影响命令能否执行的技术事实可以保留；“下一步建设 CUDA backend”属于维护信息。
- 软件设计中的维护成本、可维护接口和回归策略属于技术内容，不受此规则限制。
- VitePress 导航不暴露 `maintenance`；维护人员从 `CONTRIBUTING.md` 进入维护资料。

### 2.3 算法镜像、C++ 实现与框架坐标

教程以 C++ 为实现主线。Python 只在能减少数学或控制流理解成本时提供算法镜像，不建立第二套 Runtime，不要求学习者先安装 PyTorch，也不让默认 CMake、CTest 或全局回归依赖 Python 环境。

- 短控制流优先写在正文代码块中，建议控制在 10 到 30 行。
- 数值对照确实需要执行时，脚本放在对应 `code/<module>/reference/`，不混入 `src/`。
- Python 生成的 golden 作为小型 fixture 提交，C++ 测试读取 fixture；默认测试不现场重新生成。
- fixture 必须记录 seed、shape、dtype、误差容限和参考来源。
- 不复制 nano-vLLM、vLLM、SGLang 等项目的大段源码；只保留由本教程维护的最小算法表达。
- Loader、Storage/View、Benchmark、Profiling 不强行添加 Python，优先使用文件布局、对象关系和测量表。

框架信息按三级维护：`reference/framework_comparison.md` 解释系统位置，`reference/ecosystem/README.md` 负责按问题选项目，`reference/ecosystem/<project>.md` 负责单项目卡。章节 intro 只放一张小型对照表和下钻链接，不为同一项目在每章复制背景介绍。

| 资产 | 回答的问题 | 维护边界 |
| --- | --- | --- |
| 算法镜像 | 算法怎样推进 | 不处理生产级生命周期和错误恢复 |
| C++ 实现 | 对象怎样持有状态并执行 | 必须有可运行入口和错误契约 |
| 验证证据 | 实现是否正确、优化是否成立 | 固定输入、条件和通过标准 |
| 项目卡 | 成熟框架在哪里处理同一问题 | 只链接官方入口和稳定对象 |

## 3. 代码关联规则

章节正文和源码之间要用固定入口连起来，而不是只在章节末尾丢一个文件列表。

### 3.0.1 源码文件头注释

`code/` 下每个源码、头文件、测试和示例文件都要在第一条 `#include` 或 `#pragma once` 前写一个简短文件头。文件头只说明当前文件的职责，不重复 README 或正文推导。

推荐格式：

```cpp
// Chapter 04：CPU Attention kernel
// 职责：执行 row-major Q/K/V attention、causal mask 和 stable softmax。
// 契约：输入为 AttentionRequest，输出写入 output；失败返回 Status。
// 验证：code/chapter04_attention/tests/chapter04_attention_test.cpp
```

按文件类型调整第二、三行：

| 文件类型 | 文件头至少说明 |
| --- | --- |
| 公共头文件 | 所属层、公开接口、输入输出契约 |
| `.cpp` 实现 | 实现对象、使用的契约、主要数据布局 |
| 测试文件 | 覆盖的行为和测试入口 |
| 示例文件 | 演示场景、运行入口、关键输出 |
| 脚本 | 构建范围、隔离 build 和执行内容 |

文件头保持 3 到 5 行；局部算法只有在 stride、量化布局、生命周期或溢出处理不直观时再补行内注释。禁止使用“本文件用于帮助理解”“负责承接上下文”等无法验证的表述。

### 3.0 正文与练习的职责边界

后续 Chapter 如果同时有正文和练习，沿用 Foundation 的分工：

- 正文解释问题、概念、设计取舍、最小实现和本页验证，回答“为什么这样做、代码如何工作”。
- 练习提供 starter、任务约束、完成标准和可执行验证，回答“需要改什么、什么结果算完成”。
- 正文入口只保留学习顺序和对应练习路径，不复制题目清单、编译命令和完整验收表。
- 练习 README 负责该资产集合的目录、推荐顺序、运行方式和整体完成标准；单题 README 只负责当前题目。
- 两边允许保留一行交叉映射，但同一张路线表、资产表或验收表只维护一份。

### 3.1 章节导读页必须给出行动顺序

- `intro.md` 前半部分必须出现一个最小可运行结果
- 阅读顺序最多列 3 到 7 个页面，并说明每页产出
- 前置阅读、源码入口和相关阅读合并到行动顺序之后
- 中文章节页不单独维护 `English anchors`，英文导航放到英文镜像页里

### 3.2 关键实现页必须能直达源码

- 需要看实现的关键小节，必须在靠前位置给出源码链接
- 默认优先级是：
  - 前置阅读
  - 源码直达
  - 相关阅读
- 链接目标应优先指向具体源码文件，其次才是章节代码入口页

### 3.3 概念页和兼容页只保留轻量入口

- `complexity`、`background` 和兼容页不要放过多源码链接
- 如果需要回看，只保留少量最关键入口
- summary 在迁移期间只负责承接旧链接，不再承担收口或重讲实现
- summary 里不要再单独加 `English anchors` 段

### 3.4 代码入口要服务阅读顺序

- 代码入口不是仓库目录导航
- 代码入口要告诉读者“先看哪个文件”
- 如果一个页面没有明确的源码顺序，就不要硬塞很多链接

### 3.5 学习计划只做编排

- 学习计划负责选择哪些章节必读、哪些页面选读、需要修改什么代码以及怎样验收。
- 正文负责解释技术问题和当前实现，不保存某套计划的勾选状态、任务编号或阶段进度。
- 多套学习计划可以复用同一章节；计划之间不通过正文互相跳转。

## 4. 正文叙事规则

正文不是提纲列表，正文要先讲清楚问题是怎么出现的、为什么这样解、这样做带来什么后果。

### 3.1 先讲场景，再讲条目

- 先用连续文字说明这一页要解决的具体场景
- 再解释为什么这个问题在主线里重要
- 最后才列出设计、验证或失败模式

### 3.2 列表只负责收束，不负责开场

- 章节开头不要直接堆 `Goal`、`学习目标`、`设计要点`
- 列表适合放在解释段落之后
- 列表适合做约束、验证和失败模式，不适合承担主要叙事

### 3.3 每页至少回答四件事

- 这一页要解决什么
- 为什么现在要解决
- 最小设计是什么
- 怎么验证和接回主线

### 3.4 结尾要回到主线

- 每页最后要说明它如何接到下一页
- 不要只写复述式总结
- 不要让读者看完后还不知道下一页为什么必须接上来

## 5. 写作原则

### 3.1 先写问题，再写实现

每章开头先回答：

- 这一章解决什么问题
- 这个问题为什么重要
- 这一章做完后能得到什么
- 这一章的背景是什么
- 这一章的设计是怎样一步步推出来的

不要一上来就堆代码或接口细节。

### 3.2 每章必须收口

每章 `intro.md` 的验证末尾只需要回答：

- 本章解决了什么
- 本章完成后能做什么
- 下一章为什么必须接上来
- 暂时不做什么，以及下一章在哪里继续

收口应尽量简短、明确、统一。

建议章节收口直接写入 `intro.md`，不再把 `summary.md` 写成背景、推导和源码导航的重复页。

### 3.3 概念和实现同步出现

不要提前堆太多概念。

- 在需要 `Tensor` 的地方再讲 `Tensor`
- 在需要 view 语义时再讲 `reshape` 和 `slice`
- 在需要性能时再讲 `KV Cache`
- 在需要压缩模型时再讲量化

### 3.4 章节之间要写桥

章节正文和 `intro.md` 都要写清楚前后关系：

- 前一章补了什么前提
- 这一章补了什么缺口
- 下一章为什么必须接上来

章节正文还应该保留中间推导，不要只留结论。

- 从问题到方案的关键约束是什么
- 为什么不是别的方案
- 设计的转折点在哪里
- 这个选择带来了什么 tradeoff

桥接句要短，不要重复长篇解释。

### 3.5 进阶内容固定挂尾部

进阶内容不要打散主线，统一放在：

- `Advanced Notes`
- 章节末尾边界说明
- 附录案例页

进阶内容的作用是扩展，不是抢主线叙事。

### 3.6 语言风格保持平实

- 主线正文尽量采用中性的工程表述，少用直接对读者说话的第二人称句式
- 学习目标使用“动作 + 对象 + 条件 + 验证结果”，避免只写“理解”“掌握”“能带走什么”
- 优先使用“本章”“这一页”“系统”“实现”“验证标准”“本页产物”等客观说法
- 少用“你要”“你应该”“你现在应该能”“帮助你”“让你更容易”等口语化或目的模糊的提示
- “如果你想……”改成“需要……时，参见……”，除非页面确实是面向用户的决策入口
- FAQ 和维护文档可以保留少量指引式表达，但正文和章节导读应保持克制
- 不要把讲解写成对话，也不要把收口写成口头提示

### 3.7 删除无效抽象

- 少用“边界、职责、主线、闭环、桥接、收口、能力”等抽象名词连续成句
- 每出现一个抽象词，都要紧跟一个可观察对象：文件、命令、输入、输出、状态或测试
- “本页要解决什么”只保留在确实没有更具体标题的页面；优先改成动作标题，例如“让请求从排队走到完成”
- 不重复说明“本章不实现完整系统”；只在首次进入该主题时说明一次，后续用链接代替
- 不用“帮助读者理解”“方便后续扩展”“形成完整闭环”等无法验证的结论作为段落结尾

## 6. 术语规范

### 4.1 中英文保持稳定

一旦选定术语，后续章节尽量不要反复改写。

建议优先统一以下术语：

- `Tensor`
- `ModelLoader`
- `MatMul`
- `Attention`
- `LayerNorm`
- `FFN`
- `KV Cache`
- `Sampler`
- `Quantization`
- `Benchmark`

正文页面以中文为主，必要技术名词保留英文即可。仓库首页和教程总入口应先满足中文读者；如需照顾非中文母语学习者，可以另外保留一个轻量英文导航页。`README` 和生态索引页可以中英混排，但正文不写大段英文模板。完整语言策略见 [language_strategy.md](./language_strategy.md)。

正文里建议优先保留三类内容：

- 背景说明
- 中间推导
- 具体例子和失败模式

如果这三类内容太薄，初学者会只看到结论，看不到思路。

### 4.2 术语第一次出现时要定义

第一次出现专业名词时，建议给出简短定义。

例如：

- `KV Cache`：缓存历史 token 对应的 K/V，避免重复计算
- `reshape`：只改变形状，不复制底层数据
- `slice`：返回共享底层存储的视图

### 4.3 避免同一概念多种写法

例如下面这些写法不建议混用：

- `autoRegression`
- `autoregressive`
- `auto-regression`

应固定一种写法，全文保持一致。

## 7. 标题规范

章节标题应满足以下要求：

- 标题尽量短
- 标题要表达该章核心问题
- 序号和内容顺序一致
- 不要让标题只像内部备注
- 标题优先表达问题，不优先表达实现细节

较好的标题示例：

- `先把权重安全地读进来`
- `让张量共享数据而不是重复拷贝`
- `先把最核心的矩阵乘法跑稳`

不建议的标题示例：

- `misc`
- `temp`
- `final version`
- `new chapter`

### 5.1 章内小节建议编号

如果一篇文档的小节较多，建议给 `##` 和 `###` 标题加编号，但只在**单个文件内部**生效，不做全仓库统一编号。

推荐规则：

- `## 1. 背景是什么？`
- `## 2. 中间推导是什么？`
- `## 3. 常见失败模式`
- `## 4. 这一章要解决什么`
- `## 5. 本章目标`
- `## 6. 本章产出`
- `## 7. 学习后应能做什么`
- `## 8. 实现路径`
- `## 9. 验证方式`
- `## 10. 图示与表格建议`

如果某一章的小节数更少，可以从 `1` 开始按实际内容顺序编号，不必强行凑满 10 个。

### 5.2 编号规则

- 只给章内小节编号，不给整篇 `#` 标题编号
- 编号从 1 开始，按阅读顺序递增
- 新增小节时，后面的编号顺延
- 同级标题保持同一种编号格式
- 如果有二级子节，可以用 `1.1`、`1.2` 这种格式，但默认尽量不要超过两级

### 5.3 适用范围

- `intro.md` 优先编号；兼容页不再扩展章节编号
- `foundation` 和主线章节优先统一
- 附录只在小节较多时再编号，不强制所有页都编号

## 7. 命令和代码示例

### 6.1 命令块必须可执行

所有 shell 示例应尽量满足以下要求：

- 可以直接复制执行
- 路径尽量完整
- 不依赖模糊上下文
- 如果需要前置目录，先说明再执行

### 6.2 代码块要说明用途

每个较长代码块前最好有一句说明：

- 这段代码做什么
- 为什么需要它
- 运行后应该看到什么

### 6.3 示例不要同时做太多事

如果一个命令块同时包含下载、构建、运行、验证，建议拆成多个步骤。

这样读者更容易定位错误。

### 6.4 示例代码只承载当前章必要内容

- 不要用示例代码顺手引入下一章的大量概念
- 不要用一个代码块同时解释设计、实现和优化
- 示例的职责是帮助理解当前章，而不是提前讲完整个教程

## 7. 图示与版式

这套教程里的图优先选择低门槛、易维护的形式。

### 7.1 优先级顺序

- 表格
- 纯文本流程图 / ASCII 图
- Mermaid
- SVG

暂时不会 Mermaid，也不影响写教程。
先用表格和纯文本图把结构讲清楚，等内容稳定后再考虑用 Mermaid 美化和统一排版。

### 2. 什么时候用什么

- **表格**：职责对比、测试分层、参数说明、边界对照
- **纯文本图**：临时草图、状态流、简单流程、还没想稳定的结构
- **Mermaid**：流程图、状态机图、时序图、架构图
- **SVG**：稳定且复杂的结构图，需要长期保持版式时再用

### 3. 写作建议

- 不要因为不会 Mermaid 就卡住正文
- 先把逻辑写清楚，再考虑图形化
- 图的作用是帮助理解，不是增加装饰
- 如果一张图要花很久，先用表格或纯文本替代

## 验证方式

每章都应该有明确的验证方式，至少一种：

- 输出形状检查
- 数值对比
- 单元测试
- 端到端推理结果
- 性能指标

如果可能，尽量让验证结果可重复。

验证描述要和章节目标对应，不要只写“有测试”，要写“测试在验证什么”。

## 内容边界

每章尽量只解决一个主问题。

例如：

- `chapter01_tensor_loader` 重点是 Tensor 和模型加载
- `chapter02_tensor_ops` 重点是 view 语义
- `chapter03_matmul` 重点是线性代数算子
- `chapter04_attention` 重点是 Transformer block
- `chapter05_generation` 重点是端到端生成
- `chapter06_quantization` 重点是量化推理
- `chapter07_benchmark` 重点是测试和性能评估

如果某章开始同时讲太多内容，建议拆章。

如果某章开始承担桥接职责，应在 `intro.md` 的验证末尾写出它连接的前后章节。

## 常见问题

### 问题 1：只写目标，不写结果

不好：

- “实现一个模型加载器”

更好：

- “实现一个模型加载器，并能打印所有 tensor 的名称和 shape”

### 问题 2：只讲概念，不给验证

不好：

- 只讲 `KV Cache` 的原理

更好：

- 讲完原理后，给出一次生成前后对比，说明它减少了重复计算

### 问题 3：章节边界过宽

不好：

- 一章里同时讲 Tensor、MatMul、Attention、Generation

更好：

- 按计算路径拆成多个章节逐步推进

### 问题 4：收口太散

不好：

- 这一章学完了，下一章大概会更深一点

更好：

- 这一章完成后，读者可以……
- 下一章必须接上来，因为……

## 推荐流程

当你新增一章时，建议按这个顺序写：

1. 先写章节标题和问题
2. 说明为什么这个问题重要
3. 列出章节结束时的具体产物和验证标准
4. 再写实现步骤
5. 最后写验证方式和总结

如果章节要做桥接，推荐在 `intro.md` 中直接写“本章解决了什么 / 下一章为什么必须接上来”。

这样可以避免先写细节，后面发现章节结构不成立。

## 提交前自检

在提交教程修改前，建议做下面的检查：

- 标题是否准确
- 术语是否统一
- 中英文风格是否统一
- 示例命令是否完整
- 验证标准是否明确
- 是否存在拼写错误
- 是否有章节内容越界
- 是否按收口标准写清了当前章边界和验证条件
- 是否把模糊学习目标改成了可观察动作
- 是否把进阶内容放进了章节尾部

## 最后建议

教程最重要的是可教、可学、可验证。

如果某段内容不能帮助读者完成这三个目标，它就应该被删减、后移，或者改写成附录参考。
