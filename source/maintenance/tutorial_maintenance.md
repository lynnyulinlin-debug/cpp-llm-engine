# Tutorial Maintenance 教程维护文档

本文档面向未来的项目贡献者，定义这套教程的最终维护规范。核心目标是让主线一直清晰、可走通、可验证，并且支持后续持续增量而不破坏整体结构。

## 1. 维护目标

这套教程的目标不是追求“内容最多”，而是保持下面几件事长期成立：

- 主线清晰，读者可以按章节顺序学下去
- 每章都有明确产物和验证方式
- 文档描述与代码实现保持一致
- 术语、风格和命名尽量统一
- 章节之间的桥接稳定，读者能顺着读完主线
- 进阶内容固定挂在尾部，不打散主线

## 2. 当前阶段

当前阶段已经进入 V2，不再是“最小可用实现”阶段。

V2 的重点是：

- 让主线更顺
- 让章节边界更清楚
- 让框架对照升级为场景决策树
- 让进阶内容有固定落点
- 让不同层次读者都能找到自己的入口

## 3. 工程原则

这套项目在工程上希望长期保持下面这些原则：

### 3.1 中文主线优先
   - 正文、章节说明和维护说明以中文为主
   - 必要英文只保留术语、代码标识和少量入口
### 3.2 主线优先于附录
   - 先保证 `foundation`、`chapter00` 到 `chapter07` 的主线完整
- `guides`、`reference` 和 `maintenance` 各司其职，不做第二主线
### 3.3 背景和中间推导优先于结论堆砌
   - 每章先讲背景，再讲推导，再讲实现和验证
   - 初学者最缺的是“为什么这样走到这里”
### 3.4 章节职责必须单一
   - `foundation` 负责进入主线前的准备
   - `chapter00` 负责第一次跑通
   - `chapter01` 到 `chapter07` 负责主线推进
### 3.5 概念和实现同步出现
   - 只有在需要时才引入新概念
   - 不提前堆过多背景，避免主线失焦
### 3.6 正确性和性能分开
   - 单测和 e2e 负责“对不对”
   - benchmark 负责“快不快”
   - profiling 负责“为什么慢”
### 3.7 测试分层推进
   - `chapter00` 用 smoke test
   - `chapter01` 到 `chapter06` 用 `assert` 或最小测试
   - `chapter07` 用统一测试 harness 收口
   - 未来若复杂度上升，再从 `chapter07` 迁移到 Google Test
### 3.8 外部框架只做参考，不做主线
   - `llama.cpp`、`vLLM`、`SGLang`、`TensorRT-LLM`、`Ollama`、`Gemma` 都是坐标，不是教程本体
### 3.9 保持可验证、可比较、可迁移
   - 每章都要能验证
   - 每次优化都要能比较
   - 整条主线要能迁移到自己的工程里
### 3.10 维护文档与学习文档分工明确
   - `USAGE.md` 给学习者
   - `tutorial_maintenance.md` 给未来的项目贡献者
   - `chapter07` 的测试收口同时服务学习者和贡献者，但描述要分层
### 3.11 先收口，再扩展
   - 先把当前主线压实
   - 新内容只挂在明确的桥接点、进阶点和附录点上
### 3.12 保持教程是教程，不是百科
   - 只写当前主线真正需要的内容
   - 框架对比和背景材料都应该服务于主线，而不是替代主线

## 4. 维护原则

### 4.1 先保证主线，再补充分支

优先维护以下主线内容：

- 环境准备
- Tensor 与模型加载
- 基础算子
- MatMul 和 Transformer 核心模块
- 生成、量化、测试与 benchmark

只有当主线完整后，才考虑增加更细的分支内容，例如：

- 更多模型格式
- 更多后端实现
- 更多工程化优化
- 更多框架对比

### 4.2 先补桥，再补深度

章节维护的优先顺序是：

1. 先把上一章和下一章的桥接写顺
2. 再补这一章内部的深度说明
3. 最后再考虑进阶内容和案例扩展

如果桥接还不稳，不要先加新功能或新案例。

### 4.3 每章必须回答三个问题

每一章都应该明确写出：

- 本章要解决什么问题
- 本章完成后可以验证什么
- 本章和前后章节是什么依赖关系

如果一章不能回答这三个问题，说明章节粒度需要重构。

### 4.4 每章必须有收口

每章结尾必须能明确回答：

- 这一章解决了什么
- 这一章完成后能做什么
- 下一章为什么必须接上来
- 边界是什么
- 进阶扩展放在哪里

收口要短、硬、统一，不要一章一个风格。

### 4.5 概念和实现同步出现

不要提前堆太多概念。

- 在需要 `Tensor` 的地方再讲 `Tensor`
- 在需要 view 语义时再讲 `reshape` 和 `slice`
- 在需要性能时再讲 `KV Cache`
- 在需要压缩模型时再讲量化

这样读者更容易建立真实的心智模型。

### 4.6 框架对比只做参照，不做主线

教程里外部框架的角色建议固定如下：

- `llama.cpp` 作为本地推理 baseline
- `Gemma` 作为模型家族示例
- `Ollama` 作为本地包装和交付参照
- `vLLM` 作为云端 serving 和调度参照
- `SGLang` 作为应用编排和 structured serving 参照
- `TensorRT-LLM` 作为高性能 GPU engine 参照

不要把这些项目写成同一层级的章节主线。

### 4.7 框架参考必须按场景决策

框架参考页不写“框架百科”，只写“场景决策树”。

读者应该能从页面里直接回答：

- 我是先跑起来，还是先做服务？
- 我更关心吞吐、编排，还是 GPU 性能？
- 我是在端侧、本地、云端，还是分布式场景？

### 4.8 测试也要分层

测试框架不需要在所有章节里一开始就完全统一，建议按阶段分层：

- `chapter00_quickstart`
  - 使用 smoke test 和命令行验证
- `chapter01` 到 `chapter06`
  - 使用章节内最小可执行测试或 `assert` 级测试作为过渡
- `chapter07`
  - 统一引入正式测试体系，承担命名单元测试和端到端测试

原则是：

- 正确性测试和 benchmark 分离
- 章节内测试先保证当前模块可用
- 最终统一测试体系放在 benchmark 章节收口

| 阶段 | 主要测试方式 | 目标 | 说明 |
| --- | --- | --- | --- |
| `chapter00_quickstart` | smoke test / 命令行验证 | 快速确认环境和链路能跑通 | 关注启动、路径、模型下载和首次推理 |
| `chapter01` - `chapter06` | 章节内最小测试 / `assert` / 小脚本 | 验证当前模块语义正确 | 关注 Tensor、算子、量化等局部正确性 |
| `chapter07` | 正式测试体系 / 端到端测试 | 统一正式测试体系 | 关注回归、可维护性和跨模块一致性 |

测试方式的选择原则：

- Smoke test 先解决“能不能跑”
- 章节测试再解决“当前模块对不对”
- 正式测试体系负责“长期可维护的标准测试”
- Benchmark 只回答“快不快”，不回答“对不对”

## 9. 文档同步规则

为了避免 `README`、使用文档和维护文档各写各的，当前同步规则固定如下：

### 9.1 章节目录使用镜像脚本

- `scripts/migrate_chapter_to_source.sh` 负责章节目录镜像
- `docs/chapterXX_*`、`docs/foundation`、`docs/guides`、`docs/reference`、`docs/maintenance`、`docs/appendix` 都应通过脚本映射到 `source/` 下的对应目录
- 章节目录不要手工在 `docs/` 里复制一份后再长期维护

### 9.2 共享入口文档使用同步脚本

- `scripts/sync_shared_sections.py` 负责中文共享入口同步
- 当前它维护两组映射：
  - `README.md` -> `docs/README.md`
  - `USAGE.md` -> `docs/guide.md`
- 这些页里凡是属于共享章节的内容，先改源文件，再运行同步脚本
- 站点页中的链接要使用站点路由写法，避免把仓库相对路径原样带进 VitePress

### 9.3 英文入口单独处理

- 英文类文档使用单独脚本，不和中文同步规则混用
- `scripts/sync_english_sections.py` 负责 `docs/en/README.md` -> `docs/README.en.md`
- 英文入口页可以保留自己的措辞，但章节顺序、路由和覆盖状态要保持可检查
- 如果后续还要扩展更多英文页，优先继续追加英文脚本的映射表，而不是回退到纯手工维护

### 9.4 站点层内容保持手工维护

- `docs/index.md`
- `docs/code/`
- `docs/.vitepress/config.mts`

这些内容和正文同步不是一类问题，应该单独维护或单独生成，不要混进章节镜像脚本。

### 9.5 验证顺序

每次修改完同步规则后，按这个顺序检查：

1. 运行对应同步脚本
2. 先执行 `npm run docs:check-links`
3. 再执行 `npm run docs:build`
4. 如果构建失败，先查站点路由和相对链接，再查正文内容

如果后续还要继续调整章节内容或新增章节，优先使用仓库根目录下的 `scripts/migrate_chapter_to_source.sh` 保持迁移和映射方式一致。

## 9. 章节间代码复用方式

这套教程的代码目录是“按章节拆分”，不是“按功能彻底隔离”。也就是说：

- 每章保留自己的最小可运行代码
- 真正稳定、会被多章反复使用的基础能力，可以抽成公共层
- 不要为了“共享”而把章节骨架揉在一起

推荐的复用顺序是：

1. 先看本章导读里的 `代码入口`
2. 再进入本章代码索引页，确认本章有哪些源码、测试和脚本
3. 如果某一段逻辑后续章节会继续复用，优先在文档里说明“它属于哪一章的基础能力”
4. 如果确实要抽公共代码，优先放到明确的公共目录或公共 target，而不是直接跨章节拷贝

当前仓库的约定是：

- `chapter00` 到 `chapter07` 都保留章节级代码索引页
- 正文小节有对应代码时，页首加“对应代码”链接
- 复用关系优先写在文档里，代码层再决定是否抽公共模块

这样做的目的是让读者先知道“怎么用”，再决定“代码放哪儿”。

## 9. 文档到代码映射

当前在线文档的代码跳转，不直接指向仓库外部的 `code/` 目录，而是先进入站内的代码索引页，再按章节查看源码文件、测试和脚本。

当前约定如下：

- `chapter00_quickstart`、`chapter01_tensor_loader`、`chapter02_tensor_ops`、`chapter03_matmul`、`chapter04_attention`、`chapter05_generation`、`chapter06_quantization`、`chapter07_benchmark` 都保留一个站内代码索引页
- 章节 `intro.md` 的本章概览里只保留一个明确的“代码入口”链接
- 有对应代码的正文小节也要在页首增加对应代码链接，优先指向本章代码索引页；如果某一节对应单个明确源码文件，再补具体文件链接
- 代码索引页负责列出源码文件、测试文件和运行脚本
- 后续如果仓库接入远程代码托管，再考虑补外部源码直链

这样做的目的，是先让读者在在线教程里形成“文档 -> 代码 -> 测试 / 脚本”的稳定路径，同时避免把正文拆得太碎。

- 同一章内，intro 和 summary 的结构尽量保持同类章节一致，减少读者重新适应成本

这套规则向其他章节推进时，优先级如下：

1. `chapter07_benchmark`
2. `chapter03_matmul`
3. `chapter04_attention`

推进时先保证结构一致，再补细节和进阶内容。

- 本地构建验证

  - 再跑一次 `npm run docs:build`
  - 如果章节结构有明显变化，再补一次本地预览检查

  - 检查章节内锚点链接是否仍然可跳转
  - 检查跨章节链接、附录链接和维护文档链接是否失效
  - 如果有镜像页或索引页同步，顺手检查这些页面的引用是否还正确

## 9. 章节维护流程

当你要新增或修改章节时，建议按下面顺序处理：

1. 先写清楚章节要解决什么问题
2. 再确认前置章节依赖
3. 补充一个最小可验证结果
4. 最后再写实现细节

如果涉及桥接或收口，先统一章节边界，再补正文。

如果章节涉及代码修改，建议同时检查：

- 文档中的目标是否和代码行为一致
- 示例命令是否仍然可执行
- 验证结果是否还成立
- 在线文档镜像是否已经同步
- 本地构建是否通过
- dead link 是否清理干净

如果是按优先级推进主线章节，建议直接按下面顺序落地：

1. 先改 `chapter07_benchmark`
2. 再改 `chapter03_matmul`
3. 最后改 `chapter04_attention`

每完成一章，就做一次完成验收，不要攒到最后一起查。

  - 实现路径
- 正文
  - 一个概念点对应一个实现步骤
  - 每一步都有可运行或可验证的结果
- `summary.md`
  - 本章解决了什么
  - 本章关键结论
  - 下一步是什么
  - 收口结论
  - 边界说明
  - 进阶扩展

## 11. 文档更新检查清单

在提交文档修改前，建议检查以下项：

- 标题和章节编号是否一致
- 中英文术语是否统一
- 拼写错误是否修正
- 命令行示例是否仍可执行
- 是否说明了验证方式
- 是否说明了失败时怎么排查
- 是否避免把多个层级的内容混在一起
- 是否按收口标准写清了当前章边界
- 是否把进阶内容放进了章节尾部
- 是否完成在线文档镜像映射
- 是否完成 `npm run docs:check-links`
- 是否完成本地构建验证
- 是否完成 dead link 检查

## 12. 版本维护建议

如果教程内容开始稳定，建议再做两类管理：

- 目录索引页
  - 明确章节顺序
  - 标注每章适用场景
- 变更记录
  - 记录新增章节
  - 记录重大术语调整
  - 记录依赖版本变化
  - 记录收口规则变化

这样后续更新时，不会把教程改散。

## 13. 什么时候需要重构教程

出现以下情况时，建议考虑重构而不是局部修补：

- 同一章同时承担太多功能
- 读者在某章需要回头补太多前置知识
- 章节之间的顺序已经不再自然
- 代码实现和文档叙述偏离太多
- 框架对比内容开始挤占主线篇幅

## 14. 建议的维护节奏

- 小修订：修正拼写、命令、链接、术语
- 中修订：补充验证步骤、重排章节说明
- 大修订：重构目录、拆分章节、调整学习路径

建议优先顺序：

1. 入口链条
2. 章节桥接
3. 收口标准
4. 进阶分支
5. 生态对照

## 15. 最后原则

这套教程的维护目标不是“把每个技术点都写满”，而是保持它始终像一条可走通的学习路径。
