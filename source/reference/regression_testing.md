# 回归测试

回归测试参考页讲清测试通过后如何继续做回归验证。
`chapter07_benchmark` 已经把正确性和性能收口成证据链，回归测试参考页负责建立长期可复查的测试基线。

## 1. 这页要解决什么

回归测试解决的是一个很现实的问题：  
单次通过，不代表后续改动不会把旧问题重新带回来。

如果没有回归测试，读者很容易只盯着当前功能是否可用，却忽略了这些长期风险：

- 旧 bug 被新改动重新引入
- 边界输入只在某次提交后失效
- 正常样例通过，但异常样例开始退化
- 性能看起来没坏，但长上下文或大 batch 开始不稳定

## 2. 回归测试和 e2e / benchmark 的分工

| 问题 | e2e correctness | regression test | benchmark |
| --- | --- | --- | --- |
| 目标 | 当前链路是否正确 | 旧问题是否被重新带回 | 固定条件下快多少 |
| 输入 | 典型样例 | 版本化样例集合 | 固定 prompt / batch / 硬件 |
| 输出 | 正确 / 不正确 | 是否偏离历史基线 | latency / throughput |
| 作用 | 证明这次实现没坏 | 证明历史问题没回归 | 证明性能变化是否值得 |

这三者不能互相替代。  
e2e 证明“这次能跑对”，benchmark 证明“这次快多少”，回归测试证明“这次没有把旧问题带回来”。

## 3. 回归测试应该覆盖什么

### golden corpus

golden corpus 是一组固定、版本化的测试样例。  
它不是为了覆盖所有输入，而是为了稳定覆盖最容易回退的关键路径：

- 典型 prompt
- 特殊 token 组合
- 固定长度输入
- 典型 batch 组合

这些样例一旦确定，就不应该随便改；如果模型版本、预处理逻辑或目标阈值变了，再显式更新。

### boundary shape

边界 shape 用来抓最容易被忽略的尺寸问题：

- 最小 batch
- 最大 batch
- 单 token 输入
- 长序列输入
- 非常规 shape 组合

这类样例经常能暴露 view、reshape、cache 复用和对齐假设上的问题。

### abnormal input

异常输入不是为了“让系统报错”，而是为了确认系统能稳定拒绝或降级：

- 空输入
- 非法 token
- 超长输入
- 截断后不完整的输入
- 不符合预期的 pad / truncation 组合

如果异常输入没有被单独检查，系统后面很容易在边界上产生静默错误。

### long-context degradation

长上下文退化测试关注的是：  
输入变长以后，系统是不是还保持合理行为。

常见关注点包括：

- KV Cache 是否稳定复用
- decode 阶段是否明显退化
- 内存占用是否异常增长
- 输出是否出现明显抖动

这类测试不一定看绝对性能，更看趋势是否符合预期。

## 4. 一个可维护的回归基线长什么样

可维护的回归基线通常有几个特征：

- 样例固定
- 版本可追踪
- 阈值明确
- 失败能定位到具体输入
- 结果能和历史提交对照

如果测试结果只有“过了”或“没过”，但不能说清楚哪条样例退了、退在哪一步，那它还不算真正可维护的回归测试。

## 5.1 最小基线矩阵

第一版不追求覆盖所有模型，先固定一组能在 CPU 上重复执行的样例：

| 类别 | 固定条件 | 主要断言 | 失败定位 |
| --- | --- | --- | --- |
| golden prompt | prompt、生成步数、采样策略 | token 序列或关键输出一致 | 输入 ID / 生成 step |
| boundary shape | batch=1、单 token、短序列、最大支持长度 | shape、cache length、退出码正确 | batch / sequence length |
| abnormal input | 空输入、非法 token、超长输入 | 明确拒绝或截断，不静默继续 | 输入校验阶段 |
| long context | 递增 prompt 长度 | cache、内存和输出趋势稳定 | context length / phase |
| benchmark baseline | 固定模型、硬件、batch 和 commit | latency / throughput 在阈值内 | phase / trace event |

验收顺序固定为：先跑局部测试，再跑端到端正确性，再跑固定 benchmark，最后把结果与历史基线比较。任何一层失败，都不应只用下一层的“通过”覆盖。

当前仓库的最小执行入口是 `npm run test:regression`，它串联 Foundation 12 题、Chapter 05 和 Chapter 07 的稳定入口，并检查测试结果、请求完成状态和 benchmark 正确性标记。新增基线样例时，应让失败信息包含样例名称、输入长度、请求状态和对应阶段。

## 6. 和主线章节的关系

| 章节 | 已经做了什么 | 回归测试继续补什么 |
| --- | --- | --- |
| `chapter07_benchmark` | 正确性、benchmark、结果收口 | 长期回归基线和版本化样例 |
| `chapter05_generation` | runtime、KV Cache、scheduler | 长上下文和请求生命周期的稳定性 |
| `chapter01` 到 `chapter06` | 局部模块正确性 | 关键路径是否在后续改动中退化 |

这页不替代单测和 e2e，它只是把这些测试变成长期可复查的回归基线。

## 7. 如何使用回归测试参考页

- 先用 `chapter07_benchmark` 确认当前测试矩阵已经固定
- 再把历史上容易回退的样例整理成固定基线
- 然后在新改动后重复跑这些样例，观察是否偏离历史结果

如果只保留一句话：  
e2e 证明当前链路正确，回归测试证明旧问题没有回来。
