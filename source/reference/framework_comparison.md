# Training vs Inference Frameworks 训练框架、推理框架与本教程

这页用来回答一个很实际的问题：

- 训练框架负责什么
- 推理框架负责什么
- 我们这个从零实现的 C++ 推理引擎，学的是哪一层

如果你是从某一章主线跳过来的，章节里的“生态对照”小节通常会把你直接带到这里，再继续下钻到具体框架页。

## 1. 一句话区分

- **训练框架**：负责把模型“练出来”
- **推理框架**：负责把模型“跑起来、跑得快、跑得稳”
- **本教程的推理引擎**：负责把中间原理拆开讲清楚，并搭出一个可以学习、验证、迁移的最小实现

## 1.1 指挥台与发动机

如果把这三层再压缩成一个更容易记的比喻，可以把 Python 推理框架看成“指挥台”，把 C++ 推理引擎看成“发动机”。

- 指挥台决定怎么组织请求、怎么编排流程、怎么把模型能力包装成 API 或服务
- 发动机决定热路径怎么执行、内存怎么复用、缓存怎么管理、延迟和吞吐能做到什么水平

两者不是替代关系，而是控制层和执行层的关系。
指挥台负责把任务安排清楚，发动机负责把任务真正跑好。

放到工程实践里，这通常意味着：

- Python 更适合做快速表达、工作流编排和实验验证
- C++ 更适合做性能、状态、对象生命周期和可控执行
- 真实产品往往把两者组合起来，而不是二选一

所以本教程不是在教“哪一个更高级”，而是在教“这两个层次各自解决什么问题，以及它们怎样接起来”。

## 1.2 为什么引擎层重要

引擎层是推理系统的执行核心。它不是简单地“把模型算一遍”，而是把静态模型变成可执行、可调度、可优化、可验证的运行时。

引擎层的重要性主要体现在这几件事上：

- 把模型变成 runtime
- 把正确性变成可检查
- 把性能变成可控制
- 把复杂度收进清晰边界
- 把工程问题收束成稳定接口

没有引擎层，上层框架只能组织任务，不能保证任务跑得稳、跑得快、跑得久。
有了引擎层，推理系统才真正具备对象边界、状态边界、性能边界和验证边界。

对读者来说，这意味着：

- 只会调 API，不等于理解推理系统
- 只会搭工作流，不等于理解热路径
- 真正决定 latency、throughput、cache 和 memory 的，还是引擎层

## 1.3 引擎层的结构组成

如果把推理引擎拆开看，通常可以分成下面这些层次：

| 层次 | 主要职责 | 典型内容 |
| --- | --- | --- |
| 数据对象层 | 定义数据如何被表达和共享 | `Tensor`、shape、dtype、device、storage、view |
| 加载层 | 把权重和状态读进程序 | loader、格式解析、shape 校验 |
| 算子层 | 把基础计算封装成稳定边界 | `MatMul`、`LayerNorm`、`Attention`、`FFN` |
| 结构层 | 把算子组织成可运行模块 | `DecoderLayer`、residual、mask |
| 运行时层 | 把结构放进持续推进的生成流程 | `prefill`、`decode`、`KV Cache`、`sampler`、`Scheduler` |
| 表示优化层 | 降低资源成本，同时保住精度 | 量化、反量化、scale、dtype 切换 |
| 验证层 | 证明系统真的对、真的快 | 单元测试、e2e、benchmark |
| backend 适配层 | 把通用语义接到具体实现 | CPU、CUDA、cuBLAS、kernel dispatch、engine build |

这几层合在一起，才是一个完整的 C++ 推理引擎。

它们对应的不是“代码目录随便分一分”，而是现实里的工程分工：

- 上层框架更关注任务编排
- 引擎层更关注执行细节
- 真实产品会把两者组合起来

在本教程里，这个结构会被逐章展开：

- `chapter01` 到 `chapter02`：数据对象层
- `chapter03`：算子层
- `chapter04`：结构层
- `chapter05`：运行时层
- `chapter06`：表示优化层
- `chapter07`：验证层

所以“引擎层”不是一个单独的小点，而是这套教程真正讲解的主干。

## 1.4 框架的地位和结构组成对照

如果再往上一层看，训练框架、推理框架和本教程在系统里的地位不同，结构组成也不同。

| 对象 | 系统地位 | 结构组成 | 典型产物 |
| --- | --- | --- | --- |
| 训练框架 | 上游生产系统 | 模型定义、自动求导、优化器、训练循环、分布式、checkpoint | 训练好的权重、训练日志、优化状态 |
| 推理框架 | 运行时服务系统 | 请求入口、调度、cache、streaming、backend、部署接口 | 可部署的 runtime / engine / endpoint |
| 本教程的推理引擎 | 教学与理解中间层 | `Tensor`、loader、operator、decoder、runtime、quantization、benchmark | 一条可读、可跑、可改、可验证的推理主线 |

这个对照的重点是：

- 训练框架的核心是“把模型练出来”
- 推理框架的核心是“把模型服务起来”
- 本教程的引擎核心是“把中间原理拆清楚，并搭出一个可学习的最小实现”

所以它们不是同一层级上的同类产品，而是同一条链路上的不同位置：

1. 训练框架生产模型
2. 本教程讲清从模型到运行时的关键原理
3. 推理框架把运行时做成面向服务的系统

这也是为什么本教程会同时参考训练框架和推理框架，但不会把自己写成二者的简单折中版。

## 2. 三者的主要差异

| 维度 | 训练框架 | 推理框架 | 本教程的推理引擎 |
| --- | --- | --- | --- |
| 目标 | 训练出一个可用模型 | 低延迟、高吞吐地提供推理服务 | 从零搭出一条能解释、能验证、能扩展的推理主线 |
| 核心任务 | 前向、反向、梯度、优化器、分布式训练 | forward-only、调度、KV cache、量化、流式输出 | Tensor、loader、算子、decoder、generation、benchmark |
| 主要关注 | 训练稳定性、可导性、吞吐、显存利用 | 吞吐、延迟、并发、缓存、部署 | 原理、分层、边界、验证、迁移 |
| 典型对象 | PyTorch、JAX、TensorFlow | `llama.cpp`、`vLLM`、`SGLang`、`TensorRT-LLM` | 本仓库的章节主线 |
| 输出物 | checkpoint、optimizer state、训练日志 | 可部署的 runtime / engine / serving endpoint | 一条可读、可跑、可改的教学实现 |

## 3. 训练框架的特点

训练框架最关心的是“怎么把模型学出来”。

它一般提供：

- 自动求导和反向传播
- 优化器和学习率调度
- 训练图 / eager 训练执行
- 混合精度训练
- 分布式训练和通信
- checkpoint 保存与恢复

训练框架的强项是灵活和通用。  
它允许研究者快速试不同模型结构、损失函数和训练策略。

但它不是为“单 token 推理延迟最小化”而设计的。  
所以训练框架里的表示方式、执行方式和内存组织，通常不会直接等于一个高性能推理引擎需要的形状。

## 4. 推理框架的特点

推理框架最关心的是“怎么把已经训练好的模型高效跑起来”。

它一般强调：

- 只保留 forward path
- 控制 KV cache
- 做 batching 和 scheduling
- 处理 streaming 输出
- 做量化和部署
- 追求吞吐、延迟和资源利用率平衡

这类框架的重点不是训练自由度，而是运行时效率和服务能力。

所以推理框架常常会把模型结构、缓存组织、请求调度和输出策略重新分层，而不是直接照搬训练框架的执行形态。

## 5. 本教程的推理引擎在中间层

本教程不是训练框架，也不是完整生产推理框架。  
它更像一条“把核心原理拆开，再把最小 runtime 搭起来”的学习路径。

它刻意保留下面这些东西：

- `Tensor` 的对象模型
- 模型权重加载
- 视图语义和存储共享
- `MatMul` 和 attention 的核心算子边界
- generation runtime
- 量化路径
- benchmark 和验证纪律

它刻意不做或少做下面这些东西：

- 完整训练图
- 反向传播和梯度优化
- 复杂分布式训练
- 生产级多租户 serving
- 极其复杂的调度和容错

这意味着本教程的价值在于：

- 让读者看懂训练框架和推理框架为什么长得不一样
- 让读者看懂推理引擎为什么要重新组织对象和边界
- 让读者看懂哪些部分是“模型本身”，哪些部分是“运行时设计”

## 6. 联系链路

可以把三者理解成一条链：

1. **训练框架**
   - 把模型训练出来
   - 输出权重、结构和训练产物
2. **本教程的推理引擎**
   - 从权重开始读
   - 把张量、算子、decoder 和 runtime 组织起来
   - 解释推理路径里的关键原理
3. **推理框架**
   - 把推理能力做成可部署、可扩展、可调度的服务
   - 面向吞吐、延迟和资源管理做优化

换句话说：

- 训练框架强调“学习”
- 推理框架强调“服务”
- 本教程强调“理解从学习到服务之间那层最重要的原理”

## 7. 本教程借鉴了什么

本教程主要借鉴两类思路：

### 7.1 从训练框架借鉴

- 统一对象表示
- 张量和 shape 的系统性思维
- 模型结构分层
- 以验证为中心的工程纪律

### 7.2 从推理框架借鉴

- forward-only 的执行路径
- KV cache 和请求状态
- scheduler、batching 和 streaming
- 量化与部署的现实约束

### 7.3 本教程自己的取舍

我们把上面这些思路压缩成一条更容易学习的主线：

- 先理解 `Tensor`
- 再理解 loader 和 view
- 再理解 `MatMul` 和 attention
- 再理解 generation runtime
- 再理解 quantization
- 最后用 benchmark 收口

## 8. 具体例子

如果你想把抽象分类落到具体对象上，可以先看这些代表例子。

### 8.1 训练框架例子

- `PyTorch`
  - 最常见的训练框架参考
  - 适合看 tensor、autograd、module、optimizer 和训练循环
  - 本教程借鉴的是它的对象模型和“先把表示讲清楚”的思路
- `JAX`
  - 适合看函数式风格、编译化执行和变换思维
  - 本教程借鉴的是它对“形状、变换、函数化计算”的强调
- `TensorFlow`
  - 适合看图执行、训练/推理区分和工程化部署链路
  - 本教程借鉴的是它对模型图和运行时分层的思路
- `DeepSpeed`
  - 适合看大模型训练、分布式优化和训练系统工程
  - 本教程不是复刻它的训练能力，而是借鉴“分层、可扩展、可验证”的工程态度

### 8.2 推理框架例子

- `llama.cpp`
  - 本地推理 baseline
  - 本教程借鉴它的“先跑起来”策略和最小运行时思想
- `gemma.cpp`
  - 更具体、路径更短的 C++ 示例
  - 本教程借鉴它对初学者更友好的案例驱动方式
- `vLLM`
  - 高吞吐 serving 参考
  - 本教程借鉴它的 scheduler、continuous batching 和 KV cache 组织思路
- `SGLang`
  - 上层编排和 structured serving 参考
  - 本教程借鉴它把推理组织成更高层 workflow 的思路
- `TensorRT-LLM`
  - GPU engine 和部署参考
  - 本教程借鉴它的分层方法，以及把算子、runtime 和部署串起来的方式

### 8.3 模型家族例子

- `Gemma`
  - 不是训练框架，也不是推理框架
  - 它是“被推理的对象”
  - 本教程借鉴它作为模型家族锚点，帮助读者看 loader、shape、quantization 和 benchmark 如何受模型结构影响

### 8.4 这些例子和本教程怎么对应

- 想看“对象表示和训练循环”的例子，先看 `PyTorch`
- 想看“函数式变换和 shape 视角”的例子，先看 `JAX`
- 想看“图执行和分层部署”的例子，先看 `TensorFlow`
- 想看“大规模训练系统工程”的例子，先看 `DeepSpeed`
- 想看“本地推理 baseline”的例子，先看 `llama.cpp`
- 想看“更具体的 C++ 小案例”的例子，先看 `gemma.cpp`
- 想看“高吞吐 serving”的例子，先看 `vLLM`
- 想看“上层编排”的例子，先看 `SGLang`
- 想看“GPU engine 和部署”的例子，先看 `TensorRT-LLM`
