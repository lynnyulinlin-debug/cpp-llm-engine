# 06.5 Quantized Linear 量化 Linear


对应代码：见 [本章代码索引](/code/chapter06_quantization)

## 这一页要解决什么

把反量化逻辑与 Linear 层结合，支持量化权重推理。

## 读完你应该能做什么

- 理解为什么要把 dequant 融入 Linear
- 理解量化权重推理路径如何组织
- 理解如何在不破坏接口的前提下提升效率

## 为什么这一步重要

如果每次都先单独反量化再做线性计算，性能和内存开销都会更高。把流程融合进 Linear 更符合推理实际。

## 这一页的核心内容

- 量化权重进入 Linear
- dequant 与矩阵乘法结合
- 保持外部接口不变

这一页的重点是把量化逻辑放进最常用的推理算子里，而不是做成一层独立的“后处理”。这样更接近真实工程，因为最终性能往往取决于融合程度，而不是单个算子本身。

如果接口不变，上层模块就可以无感切换量化和非量化路径。

教程写法上，建议先把“先 dequant 再 matmul”的版本讲清楚，再说明如果未来要做融合，可以把这两步挪到更贴近底层的实现里。这样读者能先建立正确性基线，再理解为什么要优化。

在后续优化中，融合通常有两种方向：一是使用 cuBLAS 等库提供的 INT8 GEMM API，把 dequant 和 matmul 合并为一次调用；二是手写 kernel，在加载权重的同时完成反量化与乘加。无论哪种方式，上层 Linear 接口都保持不变，融合只影响底层实现路径。

最小组合伪代码可以写成：

```cpp
Tensor w = dequantize(qweight);
Tensor y = matmul(x, w);
```

后续要优化时，再考虑把 `dequantize` 和 `matmul` 融合进一个更高效的 backend。

## 实现建议

- 先确保正确性
- 再考虑融合策略
- 不破坏已有 FP16 路径

## 怎么验证

- 量化 Linear 可以运行
- 结果与非量化版本接近
- 接口行为与原 Linear 一致

如果调用方看不出内部已经切换到量化权重路径，这个抽象就算成功了一半。

## 常见问题

- 量化权重和激活的路径混乱
- 先做性能优化，后发现语义错误
- 融合后不好排错
